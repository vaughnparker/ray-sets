# Turning systems (tutorial stop #6)

An interactive three.js view of the 16 → **21** refinement. A ray-set says *which*
directions you can turn; a **turning system** adds *how far* — a turn order for each
ray (4 = quarter, 3 = third, 2 = half). The freedom is scarce: only a 4-fold axis can
be dialed down, and those live only on the cube's face-rays, so just 4 of the 16
ray-sets carry more than one turning system.

## Run it
Open **`ray-set-turning.html`** in a browser. Self-contained — three.js r128 and
OrbitControls are vendored here, so it runs offline.

- **Ray-set** dropdown (grouped T / O / I).
- **Turning system** — pick among the valid ones. On the cube faces you get three:
  the **3×3×3** (all quarter turns), the **Domino** (two face-pairs dialed to
  half-turns), and the tetrahedral **edge-turning cube** (all half turns).
- Each ray is an arrow **coloured by family**, with a small **polygon** at its tip
  showing its turn order — square = 4-fold, triangle = 3-fold, bar = half-turn,
  pentagon = 5-fold. Watching the Domino, you see one family split into two turn
  orders (same arrow colour, different polygons).
- **Click a ray** to turn the bundle by *its* allowed step (`2π/n`) and watch it land
  back on itself.

## Files
| file | role |
|---|---|
| `ray-set-turning.html` | the visualization |
| `turning_data.js` | the 21 turning systems (`const TURNING`) — per-ray turn orders, `\|G\|`, names — generated by `../lib/gen_turning.py` (which wraps `turning_systems.py`) |
| `three.min.js` + `OrbitControls.js` | three.js r128, vendored locally (offline) |
| `what_is_a_turning_system.md` | the concept, plain-language |
| `turning_systems.md` | the full result: the table of all 21 and why the rest are forced |

The enumeration itself (the source of truth) is Python:
[`../lib/turning_systems.py`](../lib/turning_systems.py).
